# Patterns and Conventions

Follow these when writing or modifying code in this project.

## Sort implementation patterns

### All data access goes through the logger

This is the most important rule. Sorts must use `SortLogger` methods for every comparison and write:

```rust
// CORRECT:
logger.cond_swap_gt(arr, i, j);
logger.write_data(arr, i, value);
logger.cmp_le_accross(arr_a, i, arr_b, j);

// WRONG — works for benchmarks but produces no visualisation:
if arr[i] > arr[j] { arr.swap(i, j); }
arr[i] = value;
```

**Reading** values is fine without the logger — only writes and comparisons need logging:

```rust
let tmp = arr[i];           // OK: just reading
let pivot = arr[mid];       // OK: just reading
logger.write_data(arr, i, arr[j]);  // Must log the write
```

### Auxiliary arrays go through the logger too

When a sort needs temporary buffers:

```rust
let mut buf = logger.create_aux_arr_t(len);   // allocate
logger.write_accross(arr, i, &mut buf, j);    // copy between arrays
logger.free_aux_arr_t(&buf);                  // deallocate
```

This lets the visualiser track auxiliary memory usage.

### Generic over `<T: Ord + Copy, U: ?Sized + SortLogger<T>>`

Sort functions should be generic over both `T` and `U`. Use `U: ?Sized` when the sort needs to work with `dyn SortLogger<T>` (visualisation path):

```rust
fn my_sort<T: Ord + Copy, U: ?Sized + SortLogger<T>>(arr: &mut [T], logger: &mut U) {
```

If the sort only uses methods that are dyn-compatible (the `T`-specific ones like `cond_swap_lt`, `write_data`, `cmp_gt`), use `?Sized`. If it needs the `Sized`-only methods (like `swap<V>` or `cmp_le<V>` for a different type), omit `?Sized`.

### Parameterised sorts use const generics for booleans

```rust
pub struct MySort<S: SmallSort, const EARLY_EXIT: bool> { ... }
```

This produces separate monomorphised code paths for each flag value — the compiler eliminates dead branches entirely.

## Registration patterns

### Standalone sort: use `create_sort!`

```rust
fn my_sort<T: Ord + Copy, U: SortLogger<T>>(arr: &mut [T], logger: &mut U) { ... }
create_sort!(my_sort, "my sort", "O(N^2)", true);
```

### Parameterised family: use `sort_family!`

Look at `src/sorts/merge_sorts/combinations.rs` for a real example. The macro generates all combinations and registers each.

### Strategy-based family: use distributed slice + `#[ctor]`

Look at `src/sorts/shell_sorts/combinations.rs` for the pattern: define a slice of entries, iterate and register in a `#[ctor]` function.

## Naming conventions

- Sort families: `snake_case` for folder names (e.g. `merge_sorts/`, `shell_sorts/`).
- Sort display names: lowercase with spaces (e.g. `"merge sort top-down pp ee"`).
- Strategy types: `PascalCase` (e.g. `ReversalRotation`, `InsertionSmallSort`).
- Strategy display labels: lowercase with hyphens in `sort_family!` labels (e.g. `"reversal"`, `"ins-32"`).
- Registration functions: prefixed with `__register_` or `__sort_fn_` (generated by macros, not hand-written).

## File organisation

- Each sort family lives in its own folder under `src/sorts/`.
- Each folder has a `mod.rs` for dispatch and module declarations.
- Parameterised families have a `combinations.rs` for registration.
- Strategy traits live in `src/utils/` (rotation, gap sequences, branching).
- Every folder has a `README.md` — see the documentation maintenance guide.

## What NOT to do

- **Don't add sorts to a central list.** Registration is automatic via macros/ctor. If you find yourself editing a list of sort names, you're doing it wrong.
- **Don't use `arr.swap(i, j)` or direct assignment in sorts.** Always go through the logger.
- **Don't put sort-specific code in `utils/`.** Utils are shared building blocks. Sort-specific logic stays in the sort's own file or family folder.
- **Don't create `dyn SortLogger<T>` in benchmark-path code.** The benchmark path uses monomorphic function pointers — trait objects would defeat inlining.
